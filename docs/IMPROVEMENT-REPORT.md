# Codebase Improvement Report

> Generated by `document-this-repo` on 2026-08-10, against `63503f2`
> Based on analysis of 4 components (Bun + TypeScript, SQLite, MCP)

---

## Executive Summary

This is an unusually well-defended codebase that has just survived three rounds of adversarial
external review on its delivery core. Its concurrency invariants are documented, tested at the
state-machine level, and commented with the incident that forced each one — that discipline is
rare and worth protecting.

It also contains one **critical, independently reproduced defect**: in the durable inbox — the
component built specifically to stop message loss — a *refusal to read* becomes a *destructive
write*. When `readStateFromDisk` fail-closes (file not 0600, not owned by the current uid, or
unreadable for any reason) it returns an empty state, `ensureLoaded` marks that empty state as
loaded, and the next inbound message atomically overwrites the file with just that message.
Every previously-unread message is destroyed. On the Claude path those messages were already
acked at the broker the moment they were first persisted (`claude-server.ts:480-485`), so the
broker will never re-offer them — the loss is silent and unrecoverable. Any event that widens
the file mode (a permissive umask during a restore, a backup tool, `chmod -R` on the home
directory) or briefly makes it unreadable is sufficient. **Reproduced twice: once by the
analyst, once independently by the orchestrator.** Fix this first.

Second is a live concurrency gap: **`claude-server.ts` never received the mutex that
`codex-server.ts` has**. Its `check_messages` handler awaits a durable-store read between the
"already delivered?" filter and the point where messages are marked drawn, so two parallel calls
can present the same message twice. This is the same race (bd-21r.3) found, fixed and
regression-tested on the Codex side; the fix was never ported. Everything the third review
certified about delivery causality is true of Codex and only partly true of Claude.

Third is a disclosure rather than a bug: `shared/summarize.ts` uploads the peer's working
directory, git root, branch and up to 20 recently-changed file paths to `api.openai.com`
whenever `OPENAI_API_KEY` is present. There is no opt-out flag and no document mentions it.

**Overall Assessment**: **Needs Attention** — one critical data-loss path, one live delivery
race, one undisclosed egress. The surrounding architecture is sound.

### A note on severity, and why two "HIGH" findings were downgraded

Two findings arrived rated HIGH. Both were re-tested against the live deployment before this
report was written, and **both are latent traps rather than live defects**:

- `AGENT_PEERS_STATE_DIR` would silently disable the entire wake subsystem (the inbox writer
  honours it; every wake reader does not). Verified: the variable is unset in the environment,
  in every LaunchAgent plist, and in the Codex config. Nothing sets it today.
- A schema-rebuild migration omits the `durable` and `host` columns and was reported to clear
  every peer's durable flag. Verified by seeding a durable peer and restarting the broker:
  **the flag survives with its value intact.** Reproducing the failure requires a database that
  has the `durable` column but lacks `hermes` in the `peer_type` CHECK constraint — a state the
  current migration ordering never produces, because the hermes migration runs first.

Both fixes still belong in the backlog: the mechanisms are real, and one migration reorder makes
the second one live and destructive. But neither is hurting anything now, and prioritizing them
above the live Claude race would be wrong.

## What This Codebase Does Well

Genuine strengths worth preserving:

- **Comments record incidents, not intentions.** Nearly every defensive shape cites the review
  round or bead that forced it ("2026-08-10 second-review H1: acks used to enqueue at DRAW…").
  This is the only surviving record of which races a given line defends against. Preserve these
  citations when editing nearby code.
- **The delivery state machine is extracted and deterministically tested.** Pulling
  `DeliveryState` out of the server made interleavings testable that no integration test could
  reach. The `BARRIER:` test encodes a schedule that a reviewer proved was broken one commit
  earlier.
- **Honest guarantees.** The delivery contract says at-least-once and explains why exactly-once
  is unattainable at the model boundary, rather than overclaiming.
- **Fail-closed trust boundaries.** The secret file and DB must be regular files, current-uid
  owned, mode 0600, or the broker exits. Readiness requires an authenticated `/ready` with a
  matching DB identity; a bare `/health` 200 is explicitly insufficient.
- **Destructive operations archive rather than delete.** `gc-inboxes` dry-runs by default and
  archives by timestamped rename. The recovery tooling was built because 24 messages went
  invisible, and it shows.
- **Clean module layering.** A programmatic DFS over `shared/*` finds no import cycles, and no
  `shared/*` module imports a server or the CLI. One runtime dependency, both devDependencies
  used.

## Critical — Fix Before Anything Else

### C-1: A failed durable-inbox read destroys every unread message
- **Category**: Reliability (unrecoverable data loss)
- **Effort**: S
- **Impact**: Removes the one path in this system that loses peer messages permanently and
  silently — in the exact component built to prevent that.
- **The Problem**: `shared/codex-inbox.ts:217-260` (`readStateFromDisk`) correctly refuses to
  load a file whose mode is not 0600, whose owner is not the current uid, which is not a regular
  file, or which errors for any other reason — and returns `{ unread: [] }`. `ensureLoaded`
  (`:129-133`) then sets `loaded = true` against that empty state, and the next
  `queueLeasedMessages()` (`:149-159`) rebuilds the file from the empty in-memory map and
  atomically overwrites the on-disk copy. The safety refusal becomes a destructive write.
  The lazy-load guard at `:122-128` protects against forgetting to call `init()`; it does not
  protect against `init()` succeeding with an empty state it was never entitled to assume.
- **Why it is unrecoverable**: `claude-server.ts:470-485` persists first and acks immediately
  after a *successful* persist, with the comment "The durable copy exists — the message can no
  longer be lost." That assumption is what this bug breaks: the messages were acked at the
  broker when originally stored, so after the overwrite there is nothing to re-offer.
- **Reproduction** (orchestrator-verified at HEAD, isolated scratch dir):
  ```
  on disk before:                                  [ 1, 2, 3 ]
  [agent-peers/codex-inbox] …/me.json has mode 644, expected 0600
    — refusing to load; starting with empty inbox
  in-memory after refused load:                    []
  on disk AFTER one new message:                   [ 4 ]
  ```
- **Recommended Action**: Distinguish "file absent" (safe to start empty) from "file present but
  unloadable" (must never write). Have `readStateFromDisk` return a `trustworthy` flag — false
  for every refusal branch and every non-`ENOENT` error — and make `queueLeasedMessages`,
  `removeByIds` and `reset` throw rather than persist when it is false. Both callers already
  handle a persist failure correctly (`claude-server.ts:474-479`, `codex-server.ts:353-361`):
  they skip the ack and let the broker re-lease, which is the safe outcome. Add a test asserting
  that a wide-mode file is never overwritten.
- **Files**: `shared/codex-inbox.ts:122-133, 149-159, 217-260`

## Quick Wins — Do These First

### QW-1: Port the piggyback mutex to `claude-server.ts`
- **Category**: Reliability (delivery correctness)
- **Effort**: S
- **Impact**: Closes the last live instance of the double-delivery race the last three review
  rounds were spent eliminating.
- **The Problem**: `claude-server.ts:285` awaits `inboxStore.getUnreadMessages()` inside the
  `check_messages` handler, between the `delivery.isBlocked(m.id)` filter at `:286` and
  `delivery.draw(callId, drawnIds)` at `:303`. There is no lock anywhere in the file —
  `createAsyncLock` is imported only by `codex-server.ts:75`. Two `check_messages` calls issued
  in the same batch both complete the read before either draws, so both present the same message
  ids. The handler-entry confirm block (`:198-206`) is likewise unsynchronized against a
  concurrent draw. **Verified by inspection at HEAD.**
- **Recommended Action**: Introduce `const withInboxLock = createAsyncLock()` in
  `claude-server.ts` and wrap the confirm block plus the read→filter→draw window, mirroring
  `acquireInboxBatch`. Add a deterministic test in the style of `tests/delivery-state.test.ts`
  that issues two overlapping handler invocations and asserts each message id is drawn exactly
  once. **Re-run the external review on this change** — it touches certified delivery semantics.
- **Files**: `claude-server.ts:198-206, 280-315`, `shared/async-lock.ts`

### QW-2: Give `shared/summarize.ts` an opt-out and disclose the egress
- **Category**: Security / Privacy
- **Effort**: XS
- **Impact**: Removes silent third-party data transmission from a tool marketed as "No cloud."
- **The Problem**: `shared/summarize.ts:42-66` POSTs the peer's `cwd`, git root, branch, and up
  to 20 recent file paths to `https://api.openai.com/v1/chat/completions` on registration
  whenever `OPENAI_API_KEY` is set. There is no opt-out (contrast `AGENT_PEERS_DISABLE_TAB_TITLE`),
  the model and timeout are hardcoded, and neither the README nor the delivery contract mentions
  it. The README's headline claim is "No cloud. No API keys between them."
- **Recommended Action**: Add `AGENT_PEERS_DISABLE_AUTO_SUMMARY=1`; consider inverting the
  default to opt-in. Document the behavior in the README environment table and note precisely
  what fields are transmitted.
- **Files**: `shared/summarize.ts:41-66`

### QW-3: Clamp `--min-age-days` to non-negative
- **Category**: Reliability (data safety)
- **Effort**: XS
- **Impact**: Prevents a typo from disabling the only safety rail on the only destructive command.
- **The Problem**: `cli.ts:784` validates with `Number.isFinite` only, so `--min-age-days -1`
  passes. The cutoff at `cli.ts:683` becomes a *future* timestamp, making `box.mtimeMs > cutoff`
  false for every file — the "too recent, may be mid-write" guard inverts and every dead inbox is
  archived, including one written a second ago. **Verified by reading the arithmetic.**
- **Recommended Action**: Reject negative values with a clear error. Archive-never-delete limits
  the blast radius, but the rail should not be disableable by a sign.
- **Files**: `cli.ts:782-786, 680-690`

### QW-4: Wrap `cli.ts` in top-level error handling
- **Category**: DX
- **Effort**: XS
- **Impact**: The recovery tool stops emitting stack traces in the exact situation it exists for.
- **The Problem**: `cli.ts:718-805` is a bare `switch` with top-level `await` and no `try`/`catch`.
  Only `status` checks broker liveness. Every other broker-touching command surfaces a raw fetch
  rejection when the broker is down — the single most likely reason to run this CLI.
- **Recommended Action**: One `try`/`catch` around the dispatch that prints a diagnosis
  ("broker unreachable at 127.0.0.1:7900 — try `launchctl kickstart -k …`") and exits non-zero.
- **Files**: `cli.ts:718-805`

### QW-5: Move the preview push out of the piggyback lock
- **Category**: Performance / Reliability
- **Effort**: XS

- **Recommended Action**: Collect the messages to preview inside the lock, fire the notifications

- **Files**: `codex-server.ts:373-400`

### QW-6: Add `try`/`catch` and typed tool errors to the Claude tool handlers

## Strategic Improvements — Plan These

### SI-1: One shared state-directory resolver
- **Category**: Architecture / Reliability
- **Effort**: S–M
- **Impact**: Eliminates an entire class of silent split-brain failures.
- **The Problem**: The inbox writer resolves its root as
  `AGENT_PEERS_STATE_DIR ?? AGENT_PEERS_CODEX_STATE_DIR ?? default` (`shared/codex-inbox.ts:99-102`),
  while `shared/wake-daemon.ts:95`, `wake-registry.ts:102`, `wake-launch-claims.ts:92` and
  `bounded-log.ts:56` consult only `AGENT_PEERS_CODEX_STATE_DIR`. Setting the general variable
  would put metadata where the daemon never looks — every peer takes the `no_pending_metadata`
  branch, which logs nothing under `--quiet-noop`. Silent, permanent no-wake. Related:
  `AGENT_PEERS_HERMES_STATE_DIR` moves the Hermes kill-switch and name-claims but not its mailbox.
- **Recommended Approach**: Add `shared/state-dir.ts` exporting one resolver per runtime; migrate
  all five call sites; add a test asserting writer and reader agree under each variable.
- **Risk if Ignored**: Latent today (nothing sets the variable) but undiagnosable when hit — the
  repair tooling looks in the wrong directory too.
- **Files**: `shared/codex-inbox.ts:99-102`, `shared/wake-daemon.ts:95`, `shared/wake-registry.ts:102`, `shared/wake-launch-claims.ts:92`, `shared/bounded-log.ts:56`

### SI-2: Make the peers-table rebuild schema-complete
- **Category**: Reliability (data integrity)
- **Effort**: S
- **Impact**: Removes a latent data-loss step that one migration reorder would activate.
- **The Problem**: `rebuildPeersTableWithNotNullSessionToken` (`broker.ts:257-289`) writes its
  column list literally, omitting `durable` and `host`. It is currently safe only because the two
  rebuild-capable migrations run *before* those columns are added — and the comment at
  `broker.ts:155-162` claiming the durable migration "MUST stay last" is already false, since
  `migrate_peers_add_host` was added after it. If a rebuild ever runs on a database that has
  `durable`, every named agent silently becomes ephemeral and is deleted 60s after it stops
  heartbeating, destroying its stable UUID and orphaning queued mail — the exact `ezra-hermes`
  incident the retention constant exists to prevent.
- **Recommended Approach**: Make the rebuild copy `durable` and `host` (guarded by a
  `columnExists` check for genuinely older databases), or generate the column list dynamically.
  Add a migration test asserting `durable` survives a rebuild — `tests/migration.test.ts` has no
  assertion mentioning it.
- **Risk if Ignored**: Dormant until someone reorders migrations, then catastrophic and silent.
- **Files**: `broker.ts:257-289, 154-165`

### SI-3: Bound the unbounded broker queries
- **Category**: Reliability / Performance
- **Effort**: M
- **Impact**: Prevents a client bug or a large backlog from turning into a 500 or a huge response.
- **The Problem**: `pollMessages` has no `LIMIT` (`broker.ts:716-725`) — a durable peer holding
  500 queued messages leases all 500 at once. `ackMessages` builds `IN (…)` with one placeholder
  per token and never caps the array (`broker.ts:760-777`), so exceeding SQLite's 999-variable
  limit turns a client bug into a 500. `readJson` performs no schema validation on any endpoint,
  so a malformed request surfaces as a raw SQLite CHECK error in a 500 — no endpoint ever returns
  400. `MAX_QUEUED_PER_DURABLE_PEER` applies only when the target is stale, so a live peer that
  never acks has an unbounded mailbox.
- **Recommended Approach**: Add a poll `LIMIT` with a documented page size; chunk ack tokens;
  add minimal shape validation returning 400. Do these together — they are one afternoon.
- **Files**: `broker.ts:662-667, 716-725, 752-810, 1412-1441`

### SI-4: Collapse the duplicated primitives
- **Category**: Maintainability
- **Effort**: M
- **Impact**: Removes ~150 lines and three cases where the tested implementation and the shipped
  implementation are different code.
- **The Problem**: Five copies of atomic-JSON-write, three `isProcessAlive` implementations with
  contradictory `EPERM` semantics, and a fixed `.tmp` filename used by multi-writer files
  (`shared/codex-inbox.ts:67`, `shared/wake-launch-claims.ts`) which defeats the atomic-rename
  guarantee when two writers alias the same path.
- **Recommended Approach**: Extract `shared/atomic-json.ts` and `shared/proc.ts`; suffix temp
  names with pid+random. Delete the confirmed-dead surface at the same time (`markSeen`,
  `getByPeerId`, `reloadMcpServers`, `EMPTY_CODEX_INBOX_STATE`, `clearTabTitle` ×2,
  `consumeUnreadMessages`).
- **Files**: `shared/codex-inbox.ts`, `shared/wake-launch-claims.ts`, `shared/wake-registry.ts`, `shared/app-server-client.ts`

### SI-5: Rewrite the README against the current code
- **Category**: DX / Correctness of documentation
- **Effort**: M
- **Impact**: Stops the front door from actively misinstructing operators.
- **The Problem**: 20+ verified inaccuracies. The most harmful: install/uninstall flows instruct
  users to find broker PIDs with `lsof -t -i:7900` and `kill -TERM` them (under launchd that
  kills a service which restarts immediately, and that `lsof` invocation returns connected
  clients too — the precise bug `kill-broker` was fixed to avoid); "Broker daemon … auto-launches
  on first session" contradicts the launchd ownership contract and the README's own line 189; the
  Shell CLI section lists 6 of 14 commands and omits the entire stranded-mail recovery toolchain;
  the environment table lists 12 of 29 variables and omits the master switch
  `AGENT_PEERS_ENABLED`; `/ready`, durable-vs-ephemeral identity, and the Hermes name election are
  never mentioned; the test count says 185 (actual: 239); uninstall deletes only the Codex state
  directory, leaving Hermes and Claude message bodies and both LaunchAgent plists behind.
- **Recommended Approach**: Keep the excellent narrative opening. Replace the operational half by
  generating it from `docs/components/cli-ops-tests.md` §2 and §3, which are already accurate.
- **Files**: `README.md` (see `docs/components/cli-ops-tests.md` §7 for the line-by-line list)

## Security Concerns

> The full assessment with 11 findings is in [issues/SECURITY-CONCERNS.md](issues/SECURITY-CONCERNS.md).
> Its S1 is promoted to **C-1** above (the highest-severity item in this report). Two further
> findings from that document are summarized here as SEC-5 and SEC-6.

### SEC-5: The wakeable Codex app-server listens unauthenticated on a TCP port
- **Severity**: High (within the same-uid trust model)
- **Description**: Wakeable mode hosts the Codex thread on an app-server bound to a local TCP
  port with no authentication. Anything that can reach that port can start turns on the live
  thread.
- **Exploitation**: Any local process can drive a real Codex session — issuing turns in a
  session that holds the user's repo access. This is a materially stronger primitive than the
  bodyless wake the daemon itself sends.
- **Remediation**: Prefer a unix socket with 0600 permissions, or require a token on
  `turn/start`. See S2 in the security document for the full analysis.
- **Files**: `shared/wakeable-launcher.ts`, `shared/app-server-client.ts`

### SEC-6: Peer-supplied text is interpolated verbatim into an instruction block
- **Severity**: Medium
- **Description**: Message bodies and peer summaries are rendered directly into the
  `[PEER INBOX]` block that the model reads as instructions, with no delimiting or escaping,
  and with no size limits anywhere (S3, S4).
- **Exploitation**: A hostile or compromised peer — or any local process that can register as a
  peer — can attempt prompt injection against a colleague agent, and can send an unbounded body.
- **Remediation**: Fence peer content explicitly as untrusted data in the rendered block and cap
  body/summary length at both broker and client.
- **Files**: `shared/piggyback.ts`, `shared/colleague-prompt.ts`, `broker.ts:609-694`

### SEC-1: Undisclosed egress of workspace metadata to a third party
- **Severity**: Medium
- **Description**: With `OPENAI_API_KEY` in the environment, peer registration transmits cwd, git
  root, branch, and up to 20 recently-changed file paths to `api.openai.com`.
- **Exploitation**: Not an attack — a disclosure failure. File paths routinely encode client
  names, product code names, and unreleased project names. A user reading "No cloud. No API keys
  between them." would not expect it, and there is no flag to turn it off.
- **Remediation**: See QW-2. **Currently dormant on this machine — the key is unset.**
- **Files**: `shared/summarize.ts:41-66`

### SEC-2: Wake metadata is read without the fail-closed permission check used elsewhere
- **Severity**: Low–Medium
- **Description**: `shared/wake-daemon.ts:247-269` reads every `*.metadata.json` with no uid/mode
  validation, unlike `shared/codex-inbox.ts:225-250` which fails closed. Any same-uid process can
  plant a metadata file and cause repeated model turns.
- **Exploitation**: A local process (or a stale file) can burn tokens by triggering wakes. Wakes
  are bodyless, so this is resource abuse, not content injection. It also contradicts the
  fail-closed claim in `docs/wakeable-codex.md:74-78`.
- **Remediation**: Apply the same uid/mode check the inbox reader uses.
- **Files**: `shared/wake-daemon.ts:247-269`

### SEC-3: `kill-broker` trusts a pid from an unauthenticated endpoint
- **Severity**: Low
- **Description**: `cli.ts:499-520` SIGTERMs the pid returned by unauthenticated `/health`.
  `broker.ts:1495-1499` explicitly stopped trusting that value for eviction because a squatter
  could name an arbitrary same-user victim; the CLI still trusts it.
- **Exploitation**: A local process squatting the port can make the operator's own CLI kill a
  process of the squatter's choosing (same uid only).
- **Remediation**: Verify the pid actually holds the listening socket, or route through
  `launchctl bootout`.
- **Files**: `cli.ts:499-520`

### SEC-4: Unauthenticated, unbounded, globally-throttled protection endpoint
- **Severity**: Low (partly by design)
- **Description**: `POST /v1/protection/check` is deliberately unauthenticated (adding auth would
  widen the shared secret's trust boundary), but it parses the request body with no size limit
  before slicing to 512 entries (`broker.ts:1412-1420`), and its throttle is a single global
  window rather than per-caller (`broker.ts:1310-1321`).
- **Exploitation**: Any local process can force unbounded JSON parsing, or exhaust the throttle
  and deny the legitimate process reaper an answer. The reaper fails safe on non-200, so the
  consequence is degraded protection, not deletion.
- **Remediation**: Add a request body size cap; keep the endpoint unauthenticated.
- **Files**: `broker.ts:1310-1321, 1412-1420`

## Cross-Cutting Patterns

### The Codex server is the reference implementation; the Claude server lags it
- **Occurrences**: Missing mutex (QW-1), missing error handling (QW-6), missing
  `Number.isFinite` guard (`claude-server.ts:532` vs `codex-server.ts:650`), `Math.max(...set)`
  spread vs iteration (`:523` vs `:648-653`), missing `myId !== again.id` rejoin guard
  (`:595-617` vs `codex-server.ts:1014`), watchdog started before vs after the enabled gate.
- **Root Cause**: Fixes were developed against Codex under review pressure and back-ported to
  Claude only when a reviewer named Claude explicitly.
- **Recommended Standard**: Any fix to a shared delivery concern must be applied to both servers
  in the same commit, or the divergence must be recorded with a reason.
- **Migration Path**: Work QW-1 and QW-6 first; then diff the two files deliberately and either
  unify or document each remaining asymmetry.

### Configuration is read from many places and validated in none
- **Occurrences**: `parseInt(AGENT_PEERS_PORT)` with no NaN guard in both `broker.ts:22` and
  `cli.ts:39` (a malformed value makes `Bun.serve` pick a random port, or produces
  `http://127.0.0.1:NaN`); the DB path re-derived in four places in `cli.ts`; state-dir precedence
  differing between writer and readers (SI-1); CLI flags parsed with `includes`/`indexOf` so
  unknown flags are silently ignored and `--min-age-days=0` silently means 7.
- **Root Cause**: Config grew organically; no module owns it.
- **Recommended Standard**: One `shared/config.ts` that parses, validates, and fails loudly at
  startup.

### Stale comments outlive the code they describe
- **Occurrences**: "MUST stay last among the peers migrations" (already false);
  "authPeer() is the only code path that touches session_token" (`authPeer` was removed);
  `listPeers` still describing opportunistic GC removed directly above it; `cli.ts:43-45`
  claiming `rename` needs no secret (it does — it calls `POST /rename-peer`); `prune`'s
  "keeps a freshly-died session visible for 30 min" (false, because `markSeen()` is never called).
- **Root Cause**: The comments are unusually load-bearing here, which is a strength — but nothing
  verifies them.
- **Recommended Standard**: When a comment states an invariant, add the test that enforces it;
  when deleting a function, grep for its name in comments.

## Methodology

Four component documentation agents worked in parallel over the broker, the MCP servers and
delivery pipeline, the wake subsystem, and the CLI/deployment/test surface; a fifth performed
cross-component conflict, dependency, dead-code and security analysis. Their red-flag inventories
were merged, deduplicated, and **re-verified by the orchestrator** before prioritization.

Verification performed directly against HEAD rather than accepted on report:

- The durable-inbox destructive write (C-1) — **independently reproduced** in an isolated
  scratch directory: three persisted messages, mode widened to 644, store re-initialized, one
  new message queued, on-disk state left holding only the new message.
- The Claude `check_messages` race (QW-1) — confirmed by reading the await sequence and
  confirming `createAsyncLock` is imported only by `codex-server.ts`.
- The OpenAI egress (SEC-1) — confirmed by reading the request construction; confirmed dormant
  (key unset).
- The durable-flag migration (SI-2) — **reported HIGH, downgraded**: a live restart test showed
  the flag surviving intact.
- The state-dir mismatch (SI-1) — **reported HIGH, downgraded**: the triggering variable is set
  nowhere in the deployment.
- The `--min-age-days` inversion (QW-3), the wake-daemon log mode (QW-7) — confirmed.
- The `bin/codex-peer` symlink `ROOT_DIR` bug — mechanism confirmed, but **latent**: the shim is
  not currently installed at `~/.local/bin/codex-peer`, so it is omitted from the ranked list.

Limitation: no runtime fault injection was performed. The concurrency findings rest on code
reading plus the existing deterministic test suite (239 tests, all passing at HEAD).
